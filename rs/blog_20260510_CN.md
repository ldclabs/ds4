# 烧了 4 亿词元！我的智能体用 DeepSeek 4 写出了 Rust 版 DeepSeek 4 推理引擎

有些 AI 编程演示，是 30 秒生成一个 todo app。

这次不是。

这次我给 Anda Bot 下了一个 `/goal`：研究 antirez 用 C 写的 DeepSeek V4 Flash 推理引擎 `ds4.c`，参考它的实现，在 `rs/` 目录下用 Rust 重写一个能跑起来、测试能过、性能尽量接近 C 版本的推理引擎。

三天时间，我们得到的是 11,748 行 Rust 代码，一个能加载 81 GB GGUF 模型、能在 Linux CPU 服务器上生成文本的 `ds4.rs`。

更有意思的是：这些代码完全由 DeepSeek 4 Pro 通过 Anda Bot 写出来。我做的事情主要是设定目标、提供真实服务器测试结果、不断纠偏，以及在它要把我电脑搞挂的时候赶紧喊停。

## 先说感谢：这个项目站在 antirez 的肩膀上

必须先把 credit 放在前面。

`ds4.rs` 不是凭空出现的。它源自 antirez 的 `ds4` 项目。antirez 是 Redis 的作者，他用 C 写出了 DeepSeek V4 Flash 的推理引擎，并公开了实现、模型格式、运行路径和大量工程细节。

我们这次做的事情，是借用并学习他的成果：研究 C 版本的结构、对齐它的模型格式和 tokenizer 行为，然后尝试用 Rust 重写 CPU 推理路径。

所以这篇文章不是“我们重新发明了 ds4”，而是：谢谢 antirez 把这样一个复杂、有趣、可研究的系统放出来；然后我们用 Anda Bot 做了一次大胆实验，看看智能体能不能独立吃下这样的工程任务。

## 我给智能体的目标

最初的目标很朴素，也很硬：

> /goal 请仔细研究这个 C 语言开发的推理引擎，参考它的实现，在 `rs` 目录下，用 Rust 重写该引擎。C 语言的单元测试也要迁移成 Rust 版本，并运行测试通过，目标是性能媲美 C 语言版本，能正常运行的 Rust 版 `ds4.rs`。

这不是一个简单需求。它包含二进制模型解析、mmap、GGUF metadata、DeepSeek V4 Flash 的固定架构、JoyAI tokenizer、KV cache、MoE routing、低比特量化矩阵乘、SIMD、Rayon 并行、CLI、测试模型生成器，以及大量 C/Rust 数值对齐。

换句话说，这是一个很适合测试长程智能体的任务：目标明确，路径复杂，中途会失败，而且最后必须用真实模型说话。

## 4 亿词元到底是什么

本地私有开发日志统计显示，这个任务从 5 月 8 日推进到 5 月 10 日，累计大约：

- 7,302 条消息
- 3,775 次工具调用
- 7,401 个模型请求
- 3.91 亿 input 词元
- 195 万 output 词元

词元费用约 80 元人民币！

这背后真正重要的不是数字本身，而是持续性：智能体需要不断读代码、写代码、跑测试、看 diff、生成 handoff、恢复上下文、处理失败、根据服务器日志继续调试。对我来说，这比单次生成一个漂亮 demo 更接近未来 AI 编程的真实形态。

## 它最后写出了什么

最终的 `ds4/rs` 是一个纯 Rust CPU 推理引擎，不依赖 Metal 或 CUDA，使用和 C 引擎相同的 GGUF 模型文件。

核心模块包括：

- `gguf.rs`：GGUF mmap 读取、metadata 和 tensor 解析
- `tokenizer.rs`：JoyAI/GPT-2 byte encoding tokenizer、BPE、特殊 token 处理
- `quant.rs`：Q2_K、Q4_K、IQ2_XXS、Q8_K、Q8_0 的 dequantize 和 dot product
- `forward.rs`：完整 forward pass，包含 attention、MoE FFN、Sinkhorn、KV cache
- `session.rs`：自回归生成会话
- `src/bin/ds4.rs`：生产 CLI，支持 one-shot 和 interactive chat
- `gen_test_gguf.rs`：生成 tiny GGUF 测试模型，避免本地依赖 81 GB 真模型

源码规模是 11,748 行 Rust。测试侧包含 158 个 `#[test]`，tiny model 下 98 个 lib 测试和 60 个 integration 测试可以通过。

## 最戏剧化的问题：我的电脑跑不动

这个项目中断过几次，最大原因不是模型不聪明，而是我的电脑不够大。

DeepSeek V4 Flash q2 GGUF 模型约 81 GB。我的开发机无法安全加载它。Anda Bot 早期两次尝试碰真实 GGUF，直接把我的电脑搞到卡死。

后来我在阿里云开了一台 64 vCPU、256 GiB RAM 的 AMD 服务器。模式变成：Anda Bot 在本地写代码和推送分支，我在服务器上 `git pull`、`cargo build --release`、跑真实模型，把输出贴回给它。它再根据日志继续修。

这也暴露出智能体系统很重要的一课：工具能访问一个文件，不代表应该读它；命令能执行，不代表目标机器承受得住。长程任务里的资源约束，必须是一等公民。

## 从乱码到可用输出

真实模型第一次跑起来后，并不是马上成功。

先是 `missing vocabulary size`。后来发现 GGUF metadata 使用 `deepseek4.*` 前缀，而 Rust 解析器只查了 `ds4.*` 和 `llama.*`。

然后是 `ĠæĢ³...` 这样的乱码。原因有两层：输出端没有正确反解 GPT-2 byte encoding；prompt template 还把 `<｜User｜>`、`<｜Assistant｜>`、`<think>` 这些特殊 token 当普通文本过 BPE，结果 prompt 被污染。

修完 tokenizer 和 prompt special token 后，模型终于开始输出可读文本。

后面还有更硬的性能和正确性问题：

- 早期 SIMD 版本 prefill 卡住
- P1-P5 优化后出现 `aplaplapla...` 循环输出
- Q2_K SIMD horizontal sum 错误
- IQ2_XXS signedness bug
- spec decode 在真实 DS4 上 0% acceptance

每一个问题都不是靠“再生成一遍”解决的，而是靠分支隔离、trace flag、C/Rust 数值对齐和真实服务器反馈一点点收敛。

## 性能结果

最终在 64 vCPU、256 GiB RAM 的 AMD Linux 服务器上，Rust v0.2.0 的表现是：

| 指标                           |  Rust v0.2.0 | C CPU reference |
| ------------------------------ | -----------: | --------------: |
| Decode，greedy，81 GB q2 model | 约 1.1 tok/s |    约 2.7 tok/s |

这不是说 Rust 版本全面超过了 antirez 的 C 引擎。C 引擎的主力路径是 macOS Metal GPU，而 `ds4.rs` 目前是 CPU-only、CLI-only，也没有 disk KV cache 和 server。

更准确地说：在 CPU reference 路径上，这个由智能体写出的 Rust 版本已经能跑真实 81 GB 模型，但 decode 速度目前仍落后于 C CPU reference。

这就已经很疯狂了。

## 这对 Anda Bot 意味着什么

这次实验让我更确信：未来的 AI 编程，不只是“生成代码片段”，而是“让智能体在一个真实仓库里长期工作”。

它需要记住目标，理解代码，失败后恢复，知道什么时候该跑测试，什么时候该开分支，什么时候该回滚，什么时候该说“这个优化看起来高级，但真实模型不接受”。

Anda Bot 的 `/goal` 模式这次扛住了一个很长的任务，也暴露出很多要改进的地方：资源约束、自动续跑、阶段验收、远程硬件反馈协议，都还可以做得更强。

但这个结果已经足够让我兴奋：一个智能体，使用 DeepSeek 4 Pro，在几天内写出了一个真实可运行的 Rust 推理引擎。

这不是幻灯片里的 AI agent，这是仓库里的 11,748 行 Rust。
